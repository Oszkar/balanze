# v0.5.2 - Legibility (docs site) - Milestone Spec

Date: 2026-07-29
Status: approved (scope), revised after review, ready for implementation plan
Phase: 5 (Distribution & Legibility), third sub-milestone

## 1. Context

The v0.5.2 milestone as originally scoped was a single issue - #210, "Docs site: mdBook skeleton + GitHub Pages deploy" - and it is already merged (`2303af5`, PR #233). The site is live at <https://oszkar.github.io/balanze/>, `book.toml` sets `src = docs/`, and `.github/workflows/pages.yml` deploys through the native Actions flow on any push to `main` touching `docs/**`.

So the tag could be cut today against a one-bullet changelog. Auditing the live site before doing that turned up defects that make the milestone worth more than a bookkeeping bump:

1. **The flagship page ships placeholders.** `docs/GUIDE.md` carries nine `📷 [capture: <state>]` lines plus an author-facing blockquote explaining the placeholder convention, all rendered verbatim on the public site. For a milestone themed *Legibility*, that is the headline defect.
2. **An internal design record is published.** `docs/reviews/surface-consistency.html` returns 200 at <https://oszkar.github.io/balanze/reviews/surface-consistency.html>, despite `docs/PRD.md` explicitly classing it as "internal engineering detail, not user-facing."
3. **There are two manuals.** `README.md` lines 57-188 (Install + Using the CLI, roughly 130 of its 241 lines) and `docs/GUIDE.md` address the same reader with overlapping content. The site inherited that overlap rather than causing it, but shipping a docs site without resolving it means paying the site's maintenance cost while keeping the drift.
4. **The published site violates AGENTS.md section 3.5.** mdBook's smart punctuation is on by default in v0.5.4 and rewrites the source's `"connecting..."` so the published HTML carries a real U+2026 ellipsis and curly quotes. The repo's staged-source punctuation sweep cannot see this, because the violation is introduced by the renderer.

v0.5.2 therefore grows from "the site exists" to **"the site is something you would send someone to."**

### 1.1 Verified facts this design rests on

Each was checked against the live site, the repo, or a local mdBook v0.5.4 run. Each drives a decision below.

**Publishing boundary**

- **mdBook skips `.md` files absent from `SUMMARY.md`, but copies non-Markdown files verbatim.** `PRD.md`, `ARCHITECTURE.md`, and every file under `docs/superpowers/` return 404 on the live site; `docs/reviews/surface-consistency.html` returns 200. The leak is structural, not a one-file mistake.

**mdBook defaults (both tested locally against v0.5.4, the pinned CI version)**

- **`build.create-missing` defaults to `true`.** A minimal book whose `SUMMARY.md` referenced a nonexistent `a.md` built successfully, exited 0, and *created* `src/a.md`. In CI that generated file is never committed, so a typo'd or forgotten chapter publishes as an empty page with a green build. A successful `mdbook build` therefore proves nothing about chapter existence.
- **`output.html.smart-punctuation` defaults to `true`.** Confirmed end-to-end rather than from documentation: `docs/GUIDE.md:60` contains `"connecting..."` with straight quotes and three periods, and the deployed `GUIDE.html` serves that same word followed by a U+2026 ellipsis and a curly closing quote. Exactly one U+2026 and zero U+2014 are live today.

**Screenshot capture**

- **All nine named capture states exist** as entries in `src/lib/gallery/fixtures.ts`.
- **Committed Playwright baselines already cover every state in both themes** (`tests/visual/gallery.spec.ts-snapshots/`), deterministic via a frozen clock and font/image readiness waits, **but they screenshot `figure.frame`, which contains the gallery's `<figcaption>` label.** They cannot be reused for the guide without embedding gallery captions in user documentation.
- **Screenshotting `.pop` instead would clip the popover caret.** `GalleryFrame.svelte` positions `.caret` at `top: -7px` against a `position: relative` `.pop`, so the caret lies outside `.pop`'s bounding box, and a Playwright element screenshot captures the bounding box only.
- **`playwright.config.ts` already declares a `webServer`** (`bun run gallery:serve`, `reuseExistingServer` off CI), so a capture run is genuinely one command.

**Content ownership**

- **`docs/TROUBLESHOOTING.md` is developer-facing, including the entries whose headings read as user symptoms.** The two tray entries resolve to "attach the handler via `app.tray_by_id("main")`, never via `TrayIconBuilder::new()`" and "check `iconAsTemplate` in `tauri.conf.json`". Those are maintainer runbook instructions, so they cannot be lifted verbatim into a public FAQ.
- **`docs/SECURITY.md` is a security policy** (supported versions, how to report a vulnerability), which GitHub surfaces in the repository's Security tab.
- **`balanze-cli` exposes ten visible top-level commands, one hidden one, and a nested action** (`crates/balanze_cli/src/cli.rs`): `status`, `watch`, `doctor`, `export`, `completions`, `setup`, `set-openai-key`, `clear-openai-key`, `settings`, `statusline`, plus `man` behind `#[command(hide = true)]` and `statusline restore`.

**Release mechanics**

- **`Cargo.lock` records workspace member versions** (`balanze`, `balanze_cli`, `anthropic_oauth`, `atomic_file`, and the rest all at `0.5.1`), so a workspace version bump is a four-file change, not three.
- **`pages.yml` triggers only on push to `main`.** It is a publish step, not a pre-merge gate, and its path filter would not fire on a README-only change at all.

## 2. Scope

### In scope

1. **Book source boundary** - move book source to `docs/src/`, making "published" a property of location rather than of file extension.
2. **Renderer hardening** - `create-missing = false` and `smart-punctuation = false`, plus a punctuation sweep over generated output.
3. **Real screenshots in the user guide** - replace all nine placeholders under an explicit asset contract.
4. **Three new chapters** - Install, CLI Reference, FAQ & Troubleshooting.
5. **README deduplication** - README keeps short-form and links down; the site owns long-form.
6. **Site branding** - a deliberately minimal stylesheet against an explicit token map, plus a favicon through mdBook's theme directory.
7. **A pre-merge documentation check** - a PR-triggered workflow that builds the book, asserts chapter existence, and link-checks the book *and* the README.
8. **Housekeeping** - PRD rewrite, changelog, version bump, release.

### The scope boundary, stated precisely

**No runtime application behavior changes.** No crate logic, no Tauri command or event, no frontend component, no settings schema. The milestone does add non-runtime code: a TypeScript Playwright capture spec, a package script, and GitHub Actions logic. Reviewers should apply the validation matrix to those (`bun run check` for the spec; YAML review for the workflow) and should *not* expect the Rust gates until the version bump in PR 4 touches the workspace `Cargo.toml`.

### Deferred

- **All application code changes.** #214, #204, #198 stay in v0.5.3. #232, #231, #219, #186, #152, #136, #134, #114, #107, #85 stay unscheduled.
- **A changelog chapter on the site.** GitHub Releases owns release history.
- **Versioned documentation** and any search configuration beyond mdBook's default.
- **A dark screenshot set.** See 3.3.
- **Moving `TROUBLESHOOTING.md` or `SECURITY.md` onto the site.** See 3.4.

## 3. Design

### 3.1 Book source boundary

`book.toml` changes `src = "docs"` to `src = "docs/src"`.

| Moves to `docs/src/` | Stays in `docs/` |
|---|---|
| `index.md`, `SUMMARY.md`, `GUIDE.md` | `PRD.md`, `ARCHITECTURE.md`, `SECURITY.md`, `TROUBLESHOOTING.md` |
| `assets/` (and the new `assets/guide/`) | `superpowers/`, `reviews/` |
| The three new chapters (3.4) | |

The resulting invariant is: **`docs/src/` is the content root, and nothing else under `docs/` is published.** Today's rule ("`.md` files are safe unless listed, other extensions always publish") is not something a contributor can be expected to hold in their head, and it fails silently.

One qualification, because the earlier draft stated this as an absolute and was wrong: mdBook's theme directory (`theme/`, a sibling of `book.toml` at the repository root) also contributes to the built site, and 3.5 uses it for the favicon. So the published surface is `docs/src/` **plus** `theme/`. `theme/` holds assets only, never prose, and it sits outside `docs/` entirely, so the rule a contributor needs still holds inside the docs tree.

Consequential edits:

- `pages.yml` path filter narrows from `docs/**` to `docs/src/**` plus `theme/**`, `book.toml`, and the workflow itself, so editing the PRD no longer triggers a Pages deploy.
- `README.md` asset references (the two logo variants, both popover screenshots, the TUI screenshot) repoint to `docs/src/assets/`.
- `docs/GUIDE.md:134` currently links to `TROUBLESHOOTING.md` through a GitHub blob URL; it becomes a relative link to the new FAQ chapter.

`docs/reviews/surface-consistency.html` needs no separate handling once the boundary moves. It is kept, not deleted: it remains a legitimate internal record.

**Alternative considered and rejected:** relocate the one `.html` file and leave `src = docs/`. Cheaper by a handful of edits, but it fixes today's instance rather than the trap, and the trap is silent.

### 3.2 Renderer hardening

```toml
[build]
build-dir = "book"
create-missing = false

[output.html]
smart-punctuation = false
```

`create-missing = false` turns a missing chapter into a build failure instead of a silently generated empty page. `smart-punctuation = false` stops the renderer from manufacturing the U+2026 and typographic dashes that AGENTS.md section 3.5 prohibits, and as a side effect keeps quotes straight, matching the source.

Neither is sufficient alone, so validation also asserts positively (see section 6): the five expected HTML pages exist and carry their expected `<h1>`, and the punctuation scan runs over `book/` as well as over the tracked sources.

### 3.3 Guide screenshots

The nine placeholders become real images and the author-facing blockquote at `docs/GUIDE.md:7` is deleted.

**Capture path.** A dedicated Playwright spec (`tests/visual/guide-shots.spec.ts`) reuses the existing config's determinism (frozen clock at `2026-01-01T12:00:00Z`, `document.fonts.ready`, image-decode waits) and its `webServer`, so the whole refresh is **one command**: `bun run guide:shots`, a new package script running Playwright against that spec. Section 5's manual tests say the same thing; the earlier draft's two-step description was wrong.

**Caret-safe framing.** The spec screenshots `figure.frame` with an explicit `clip` that excludes the `<figcaption>` box and extends the top edge upward past `.pop`'s bounding box, so the caret at `top: -7px` is inside the capture. A bare `.pop` element screenshot would clip it. Concretely: take `figure.frame`'s box, drop the caption height plus the flex `gap: 8px`, then extend the top by at least 8px. Validation asserts the caret is present, not merely that no caption is.

**Light theme only.** mdBook's theme selector is a localStorage toggle independent of `prefers-color-scheme`, so a `<picture>` element cannot track it, and `default-theme` is already `light`. Shipping one honest set beats shipping two that mismatch half the readers. Navy-theme readers see light screenshots framed by a hairline border (3.5), which reads as a deliberate inset rather than a rendering fault. A dark set is a follow-up if anyone asks.

**Density.** Captured at `deviceScaleFactor: 2` and displayed at CSS width 360px (the popover's real width), so the images stay crisp on HiDPI displays. Files land near 100KB each, which is acceptable for nine assets on a docs site.

**Asset contract.** Every image is written as `![<alt>](assets/guide/<file>.png)` followed by an italic caption line. Alt text describes what is shown for a reader who cannot see it; the caption carries the explanatory text that the placeholder line used to hold, so no information is discarded.

| File | Gallery state | Alt text | Caption |
|---|---|---|---|
| `settings-configured.png` | Settings - configured | Settings panel with the OpenAI key field filled and both provider toggles on | The settings panel after setup, keys in place. |
| `details-two-providers.png` | Cards - two providers | Details view with stacked Anthropic and OpenAI cards showing quota bars and billed spend | The default Details view, Anthropic and OpenAI side by side. |
| `overage-billed.png` | Grid - overage billed | Anthropic billed cell showing a real dollar overage amount badged as real | The Anthropic billed cell showing a real overage amount. |
| `compact-grid.png` | Grid - two providers | Compact grid with one row per provider and one column per metric | The Compact grid. |
| `openai-connect-cta.png` | Grid - OpenAI connect CTA | OpenAI cells replaced by an "add OpenAI" call to action | The "add OpenAI" affordance before a key is set. |
| `state-cold-start.png` | Grid - cold start (quota loading) | Quota cells showing loading skeletons | Cold start: a source is still connecting. |
| `state-not-detected.png` | Grid - Claude Code not detected | Anthropic cells reading "not detected" in neutral styling, no warning color | Claude Code not detected: a neutral not-configured state, not an error. |
| `state-stale-window.png` | Grid - Codex stale window | Codex cell marked stale instead of showing a number | Stale window: a window that already reset degrades to a stale marker. |
| `state-fetch-error.png` | Grid - OpenAI error | OpenAI cell showing an error placeholder above the degraded-state banner | Fetch error: the failed source is named in the degraded-state banner. |

**Sizing.** The stylesheet in 3.5 gives `.content img` `max-width: 100%` and `height: auto`, so screenshots scale down on narrow viewports rather than forcing horizontal scroll.

**Refresh discipline.** Hand-refreshed when the popover changes, in the same manual-smoke category as the visual baselines (AGENTS.md section 6). The single command makes that cheap.

**On duplicating the visual-regression harness.** This is a second capture path alongside the baselines rather than a reuse of them, and that duplication is deliberate. The baselines exist to detect unintended visual change, so they are platform-suffixed and caption-inclusive; the guide assets exist to be read by a person. Coupling a docs artifact to a test fixture's framing would make every baseline reframing a docs regression.

### 3.4 Chapters

**`index.md` - landing page.** Two journeys arrive here and they diverge immediately, so the page is ordered by that split rather than by topic:

1. One sentence of value proposition, and the popover screenshot.
2. The measured-only matrix table, because the honesty model is the product's distinguishing claim and belongs above the fold.
3. **Get Balanze**, split two ways: *Desktop tray app* (Windows 11 x64, macOS 15+ Apple Silicon) linking to Install, and *Command line* (all three OSes including Linux) linking to Install's CLI section.
4. Then, in order: User Guide, CLI Reference, FAQ.
5. A closing line to the GitHub repository for source, releases, and issues.

It stops deferring install to GitHub.

**Install** (`docs/src/install.md`) - long-form, absorbed from the README: checksum verification commands, architecture caveats (no Intel macOS, no arm64 Windows desktop), the macOS quarantine `xattr` note, Homebrew, and building from source. Sectioned desktop-first then CLI, matching the landing page's split.

**CLI Reference** (`docs/src/cli.md`) - the ten public commands enumerated in 1.1, each with its flags, plus the nested `statusline restore`, the four global flags (`-v`, `--quiet`, `--no-color`, `--strict`), the exit-code table, the `BALANZE_OPENAI_KEY` and `BALANZE_LOG` environment variables, shell completions, and a pointer to the `--json` schema in `ARCHITECTURE.md`.

`man` is hidden from `--help` deliberately, and the chapter documents it in a single aside marked as such, because it is useful to packagers and hiding it from the reference too would be an accident rather than a decision. Hand-written; no generation step, since a clap dump reads worse than prose and would add a build dependency.

**FAQ & Troubleshooting** (`docs/src/faq.md`) - assembled from the user-facing *symptoms* in `docs/TROUBLESHOOTING.md` plus the Guide's "States you might see" section, which is FAQ material sitting in a walkthrough.

**Entries are rewritten, never copied.** The rule: an FAQ answer may only prescribe actions available to someone running a released build - check a setting, run `balanze-cli doctor`, restart the app, re-run `claude login`, file an issue. Root causes and code-level fixes stay in `docs/TROUBLESHOOTING.md`. Concretely, "two tray icons" becomes "this is a bug in the build you are running, not something you can configure; please file an issue with your OS version", and the developer document keeps the `tray_by_id` explanation. Publishing "attach the handler via `TrayIconBuilder`" to users would be worse than saying nothing.

`docs/TROUBLESHOOTING.md` keeps the developer entries and gains a one-line header declaring itself developer-facing, pointing at the site's FAQ for user issues. `docs/SECURITY.md` does not move.

### 3.5 Branding

**The design position is restraint.** mdBook's defaults are already responsive, keyboard-navigable, and contrast-checked. Every property overridden is a property that can regress, so the stylesheet overrides exactly three things: link color, sidebar active color, and image framing. Typography, spacing, layout, and the search UI are left alone. This is also the honest answer to "make it look like Balanze": the mark and two accent colors carry the identity, and a hand-rolled type scale on top of a working one would be decoration with a regression bill.

**Token map.** Balanze's `--real` blue (the token that marks officially-sourced data) becomes the link color. Values are read from `src/lib/theme.css`, and mdBook's current values are from its generated `variables.css` at v0.5.4:

| mdBook variable | mdBook `.light` | Balanze light | mdBook `.navy` | Balanze navy |
|---|---|---|---|---|
| `--links` | `#20609f` | `#3667a6` (`--real`) | `#2b79a2` | `#6ea3e6` (`--real` dark) |
| `--sidebar-active` | `#1f1fff` | `#3667a6` | `#2b79a2` | `#6ea3e6` |

Overrides are scoped to `.light` and `.navy` only. The other three bundled themes keep mdBook's values; theming all five would be busywork for themes this project has no opinion about.

Contrast for the two new pairs must be verified during implementation and must meet WCAG AA (4.5:1) for body text: `#3667a6` on `#ffffff` computes to about 5.8:1, and `#6ea3e6` on navy's `hsl(226, 23%, 11%)` to about 6.7:1. Both pass with margin, but the numbers above are computed, not measured, so implementation confirms them.

**Image framing.** `.content img { max-width: 100%; height: auto; border: 1px solid var(--quote-border); border-radius: 10px; }`, which is what makes a light screenshot read as intentional on the navy theme.

**Favicon.** mdBook overrides the favicon through its theme directory, verified locally against v0.5.4: a file dropped at `theme/favicon.png` beside `book.toml` is published and the `<link rel="shortcut icon">` rewritten to point at it, with mdBook's default SVG dropped entirely rather than left alongside. Whichever format is supplied wins outright, so **only `theme/favicon.png` is shipped**, reusing the existing `src-tauri/icons/128x128.png`. No SVG favicon: `logo.svg` is 816x869, so it would letterbox in a square tab slot, and authoring a square variant is art work this milestone does not need.

**No sidebar logo.** The earlier draft specified one at 28px with a theme swap. mdBook has no configuration for it: producing it requires either a CSS pseudo-element with hand-written selectors and theme rules, or an `index.hbs` template override. The template override pins the site to one mdBook version's markup and can break silently on upgrade, and both options contradict this section's own restraint position, which is the test the rest of the stylesheet is held to. So the sidebar keeps mdBook's default.

The mark still appears where it does the most work: `index.md` opens with it as an ordinary Markdown image, using the existing `logo.svg`. That needs no mechanism, no template, and no theme-swap logic, and the landing page is the first screen anyway.

### 3.6 README deduplication contract

The README keeps short-form and links down. It never re-explains what the site owns.

| Stays in the README | Moves to the site |
|---|---|
| Pitch, badges, screenshots, the matrix table | Checksum verification commands |
| A compact install table (2 desktop rows, 4 CLI rows) | The macOS quarantine `xattr` note |
| The SmartScreen `<details>` block | `cargo install` from-source detail |
| The roughly ten-line CLI command list | Exit-code table, completions, environment variables |
| Develop, gallery, "Finding your way around", Contributing, License | The `status --json` schema pointer |

The SmartScreen block stays deliberately: it is read at the moment of download, GitHub is the distribution channel, and sending someone to a website mid-download is friction.

Expected result is roughly 150 lines, down from 241.

### 3.7 The pre-merge documentation check

`pages.yml` cannot be the gate. It runs only on push to `main` (post-merge), its narrowed path filter never fires on a README-only change, and the artifact it could check, `book/`, contains no README at all. An offline link check over `book/` would also skip every `https://oszkar.github.io/balanze/...` link the README uses to reach the site, which is precisely the navigation this milestone creates.

So the gate is a **new workflow**, `.github/workflows/docs.yml`, triggered on pull requests touching `README.md`, `docs/src/**`, `theme/**`, `book.toml`, or the workflow itself.

**It must be its own workflow, not a job in `ci.yml`.** GitHub's `paths` filter applies to the workflow's `on:` event, never to an individual job, and `ci.yml` currently triggers on every PR with no filter while owning `linux` and `deny` (the required `linux` and `cargo-deny` checks). Adding `paths` there to scope a docs job would suppress the entire workflow on non-docs PRs, leaving two required checks permanently pending and blocking every code merge. A separate workflow is the only option that scopes the trigger without touching the required checks.

The workflow:

1. Builds the book with `create-missing = false`, so a missing chapter fails here.
2. Asserts the five expected pages exist in `book/` and each carries its expected `<h1>`.
3. Runs the punctuation scan of section 3.2 over `book/` and over the tracked sources.
4. Runs `lychee` over **both** `book/` and `README.md` with:
   - `--remap "^https://oszkar\.github\.io/balanze([/?#]|$) file://$(pwd)/book\$1"` so the README's links into the site resolve against the freshly built book rather than the currently deployed one. The quoting is load-bearing and the earlier draft had it wrong: double quotes so `$(pwd)` expands in the shell, and `\$1` escaped so the capture reference reaches lychee instead of being eaten as a shell positional. This is what makes the whole workflow worthwhile - it is the only check that can catch PR 4 breaking README-to-site navigation, and it validates against the version being merged.
   - Third-party hosts excluded, so an unrelated site's downtime cannot block a docs PR.
   - Repository-relative links in the README (`docs/PRD.md`, `AGENTS.md`, `LICENSE`) checked as local files.

**The punctuation scan is a full-tree scan, not a staged-diff scan.** A CI checkout has no staging area, so the local pre-commit habit of sweeping `git diff --cached` inspects nothing there. The workflow scans the tracked files it is responsible for in full: `README.md`, `docs/src/**`, `book.toml`, `theme/**`, and the built `book/`. Full-tree is also the right choice on the merits, since the prohibition is repository-wide and a diff scan would let pre-existing violations survive indefinitely. Verified that those paths are currently clean, so the scan lands green rather than needing a remediation pass first.

`lychee` is fetched from its GitHub release and verified against a pinned SHA-256, mirroring exactly how `pages.yml` already installs mdBook and for the reason that file documents: it keeps the step fast and leaves the workspace's vetted Cargo dependency graph untouched. No third-party GitHub Action is added.

`pages.yml` keeps its own build and gains the same `create-missing` protection implicitly through `book.toml`. It is not made a duplicate of the gate; it stays a publish step.

**This workflow is not added to the required status checks on `main` in this milestone.** Required checks are currently `linux`, `cargo-deny`, and `conventional-commit title`; changing branch protection is a repository-settings action that should follow the workflow proving itself over a few PRs, not accompany its introduction.

Promoting it later is not a one-click change, and the reason is the same mechanism as the blocker above: a path-filtered workflow does not report a status on PRs that do not match its filter, so marking it required would leave every code-only PR waiting on a check that will never run. Making it required means dropping the path filter (and having it exit early on non-docs PRs) or adding a companion no-op job that always reports. Recorded so the future change is understood before it is attempted rather than discovered as an outage.

## 4. Housekeeping

- **PRD.** The v0.5.2 section is currently written in past tense as docs-site-only. It is rewritten to describe what actually shipped, and the Phase 5 summary line in "Current status" updates alongside it.
- **CHANGELOG.** The existing `[Unreleased]` docs-site bullet is joined by entries for the guide screenshots, the new chapters, and the README pass, then released under `## [0.5.2] - Legibility - <date>`.
- **Version bump, four files:** `Cargo.toml`, **`Cargo.lock`** (workspace members are recorded there and a bump rewrites them), `package.json`, `src-tauri/tauri.conf.json`. Regenerate the lockfile with `cargo check --workspace` rather than editing it by hand.

**The tag is not part of PR 4.** A git tag is not PR content, and tagging before the merged commit's checks pass would publish a release from an unverified state. Order: merge PR 4, confirm the merged commit is green, confirm the site is correct, then create and push `v0.5.2`.

**PR 4 does not deploy Pages, so "confirm the deploy" means PR 3's.** PR 4 touches `README.md`, `docs/PRD.md`, `CHANGELOG.md`, and the four version files, none of which match `pages.yml`'s narrowed filter. PR 3 is the last Pages-triggering merge in the milestone. Release validation therefore confirms the deployment published by PR 3 is live and correct; waiting on a PR 4 deploy would wait forever.

**Release (post-merge, not a PR).** Confirm the merged commit is green and that the site published by PR 3 is live and correct, then tag and push `v0.5.2`.

## 6. Validation

Per AGENTS.md section 6, mapped to what each PR actually touches.

**Every docs PR (enforced by `docs.yml`):**

## 7. Risks and open items

- **Screenshot staleness.** Nine hand-refreshed images are nine things that can drift from the UI. Mitigated by the one-command refresh and by state names matching real gallery fixtures, so a removed state fails the capture loudly rather than shipping a stale image.
- **Deduplication regressions.** Cutting roughly 90 lines out of the README risks dropping something with no new home. PR 4 is reviewed against the 3.6 table specifically, not just read for flow, and `docs.yml` catches the navigation half.
- **`docs.yml` is advisory until branch protection changes.** Until it is added to the required checks, a PR can merge with it red, and promoting it is not a one-click change (see 3.7 for the path-filter interaction). Accepted for this milestone; revisit after it has run on a few PRs.
- **`lychee` version drift.** A pinned binary plus SHA-256 means an upgrade is a deliberate edit, which is the intent, but it also means the pin will go stale silently. Same trade-off the mdBook pin already carries.
- **Chapter drift over time.** The link check catches broken links, not stale prose. Accepted: at one maintainer, the alternative is a doc-testing apparatus that costs more than the drift it prevents.

## 8. Scope calls made against review feedback

Three review points were narrowed or resolved against the obvious reading. Recorded so the omissions read as decisions.

**A full responsive and accessibility matrix** (320px and 375px and tablet and desktop, 200% zoom, screen readers, search and theme-control keyboard passes, sidebar-collapsed logo behavior, body and muted-text contrast) was scoped down to section 6's list. The reasoning: mdBook ships a responsive, keyboard-navigable, contrast-checked theme, and this milestone changes three CSS properties. Acceptance criteria proportional to the change catch regressions; re-auditing the upstream theme is work this project would not repeat and cannot maintain. If the stylesheet ever grows past the 3.5 token map, the matrix grows with it.

**The sidebar logo was cut rather than specified.** Review asked for the mechanism to be pinned down: a CSS pseudo-element or an `index.hbs` override. Pinning it down is what killed it. Both mechanisms cost more than the feature is worth here, and the template override in particular couples the site to one mdBook version's markup, which is a silent-breakage risk on every upgrade. Section 3.5 argues the stylesheet should override as little as possible; taking that seriously means the logo goes on `index.md`, where it needs no mechanism at all. Specifying the mechanism was the right ask; the answer it produced was "do not."

**A `DESIGN.md`** was not created. The substantive part of that feedback - that "accent colors are lifted from `theme.css`" left the central visual decisions to the implementer, and cited a path that does not exist - is real and is fixed by the explicit token map in 3.5, with the correct path (`src/lib/theme.css`) and exact hex values. A separate design-system document for three CSS custom properties is the speculative abstraction AGENTS.md section 2 warns against; the token map belongs in the spec that justifies it.
